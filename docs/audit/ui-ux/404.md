# UI/UX Audit — 404 Not Found (`/404`)

## Summary
The page is visually strong and on-brand, and the previously-flagged blocker is resolved: `<HelpfulLinks />` is live and rendering, so lost visitors get real recovery paths (page links, service links, a contact strip) rather than a dead end. Color usage now correctly follows the primary/interactive split introduced since the last audit. The one open issue is that the decorative "pulse" indicator ignores `prefers-reduced-motion`, which the team's own sitewide reduced-motion pass was supposed to catch.

## Findings
| Severity | Area | Finding | Recommendation | Location |
|---|---|---|---|---|
| Medium | Motion / accessibility | The pulse-dot indicator uses Tailwind's `animate-ping` directly with no `motion-reduce:` variant and no `data-animate` attribute, so it is untouched by `public/scripts/animations.js`'s reduced-motion check and never covered by any global `@media (prefers-reduced-motion: reduce)` reset (none exists in `src/styles/starwind.css`; `ComingSoon.astro` has its own scoped reset but that doesn't apply here). Users with reduced-motion enabled still get an infinitely-looping ping animation. | Add `motion-reduce:animate-none` to the `animate-ping` span, or wrap it in the same reduced-motion pattern used in `ComingSoon.astro` (lines 301-309). | `src/pages/404.astro:107-109` |
| Low | Visual hierarchy | The giant "404" numeral and the floating icon card sit at a lower visual weight (low-opacity gradient text) than a typical error page, which is a nice touch, but the icon card and the CTA row have no `data-animate` entrance treatment while other marketing pages on the site use `[data-animate]` consistently — the 404 page feels visually static/abrupt compared to the rest of the site's motion language. | Optionally add `data-animate` to the hero content block for visual consistency with other pages (low priority, cosmetic only). | `src/pages/404.astro:47-171` |
| Low | Content/SEO | Prior audit flagged verifying that Astro/Vercel actually returns a true HTTP 404 status (not a 200) for this route. Not re-verified in this pass since it's an infra/routing concern rather than UI, but still open. | Confirm via `curl -I` against a deployed unknown path that status is 404. | N/A (routing config, not this file) |

## What's Working Well
- `<HelpfulLinks />` is imported and rendered uncommented at `src/pages/404.astro:174` — confirmed **actively rendering**, not commented out. This resolves the prior audit's High-severity finding. It renders two link cards (Pages, Services, sourced from `src/data/navigation.ts`) plus a phone/contact strip, giving genuine recovery paths instead of a dead end.
- Correct primary/interactive color discipline: the "Error 404" badge, icon-card dot, and pulse animation all use `--primary` (decorative), while the "Back to Home" button and the contact-strip CTA use `--interactive` (clickable) — exactly matching the new design system split.
- Two clear, well-differentiated CTAs (primary "Back to Home" + secondary outline "Contact Us") plus the HelpfulLinks contact strip give three distinct recovery paths total.
- Background grid + ambient blobs are static (no motion), so they don't need reduced-motion handling — only the ping animation does.
- Responsive layout uses sensible breakpoint scaling for the numeral (`text-[8rem] sm:text-[12rem] lg:text-[16rem]`) and the CTA row stacks to full-width buttons on mobile (`flex-col sm:flex-row`, `w-full sm:w-auto`).
- Radius and border tokens (`rounded-lg`, `rounded-2xl`, `border-border`) are used consistently with the sitewide `--radius: 0.75rem` cascade — no hardcoded corner values.
